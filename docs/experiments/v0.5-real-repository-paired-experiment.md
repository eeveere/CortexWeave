# v0.5 Real-Repository Paired Experiment

**Status:** Revision 6 complete; narrow Helped result

Revision 2 was sealed before either scored lane ran. Revision 1 used `E0308`,
but stable `rustc` JSON does not expose its expected/actual type distinction as
structured fields. Supplying those fields would have required an operator to
infer them from diagnostic prose, violating the typed-evidence truth boundary.
Revision 2 therefore uses the analogous `E0425` undefined-identifier failure,
whose v1 signature requires no fabricated type fields. All lane controls and
interpretation rules are otherwise unchanged.

Revision 3 was likewise sealed before either scored lane ran. A typed
source-change attempt correctly makes consolidation review-required because
v0.5 cannot recover its historical code snapshot. Since review-required
proposals cannot be accepted automatically, the attempt markers now use
truthful `cortexweave.external_tool_completion` version 1 editor Events. Exact
pre/post source and BLAKE3 hashes remain sealed beside those Events as raw
experiment evidence; they are not misrepresented as CortexWeave evidence.

Revision 4 was sealed after an aborted setup-only run and before Task A
consolidation or either scored lane. The model still receives the complete real
repository, but CortexWeave indexing is fixed to `src/**`. The first setup run
showed that embedding historical plans and large documentation dominated setup
without contributing to either source repair; it also exposed a runner-only
missing Cargo `--offline` flag. Revision 4 applies the same source-only index and
offline compiler command to Task A and both lanes. Setup duration is reported
separately and is never included in scored model time.

Revision 4 later aborted without a comparative label. Its baseline model run
completed, but assisted preflight reported `no_eligible_result` before any
assisted model was dispatched. Diagnosis showed that Experience-aware context
was copying the active failure's current path and graph key into hard historical
search filters. That contradicted the already accepted compatible-component
contract and prevented a same-domain, same-component failure in a different
source location from retrieving the Task A Experience.

Revision 5 was sealed after that abort and before creating its Task A evidence
or running either scored lane. The production correction leaves explicit path
and graph-key search filters unchanged, but no longer invents them from the
active failure during context assembly. The active signature still supplies
full exact identity and compatible components; current source, task, and
failure evidence retain their existing authority and budgets. Revision 5 uses
a newly built and hashed binary, a new Task A database and repository fork, and
fresh baseline and assisted model runs. No revision-4 outcome is reused or
interpreted.

Revision 5 also aborted without a comparative label. Its new baseline model run
completed, but corrected assisted preflight found exactly one eligible
compatible Experience and could not admit it: ordinary context consumed 3,858
of the fixed 4,096-token packet, leaving 238 tokens for a conservatively counted
381-token historical item. The `budget_exhausted` result is the intended one-way
current-evidence policy, not a retrieval or authority defect. No revision-5
assisted model was dispatched.

Revision 6 was sealed after read-only budget probes on the already-aborted
assisted database and before either revision-6 scored lane. At 8,192 tokens the
Experience still did not fit. At 16,384 it fit exactly with no remaining packet
capacity. At 32,768 and 65,536 the finite ordinary candidate pool was exhausted
at the same 24,843 tokens; the 381-token Experience fit, with 7,544 and 40,312
tokens remaining respectively. Revision 6 therefore fixes both lanes at 32,768
tokens, the smallest probed non-boundary capacity. It re-seals new lane copies
of the validated immutable Task A repository/database fork, reruns both models
fresh, and reuses no revision-5 model output or lane-specific state.

This protocol evaluates one narrow question: when a fresh CortexWeave task is
given an eligible, verified Experience from a related repair, does that
historical supplement help, harm, or make no material difference? It is a
paired case study, not evidence of broad model improvement.

## Fixed subject and controls

Use the CortexWeave repository at the exact source snapshot recorded in the run
manifest. Build and hash the CortexWeave binary before injecting either
failure. The experiment must run in a disposable directory and a dedicated
SQLite database; it must never mutate the development checkout or its database.

Task B has two sequential lanes:

- **baseline:** assemble ordinary current context without an active failure
  signature, reproducing the v0.4 context condition;
- **assisted:** assemble context with the canonical active Task B failure
  signature, allowing the verified Task A Experience to be selected.

Both lanes use the same v0.5 binary and an identical copy of the post-Task-A
database. Omitting the baseline signature, rather than changing configuration
or binaries, isolates Experience selection as the intended treatment. Both
lanes keep Experience support enabled and use the same context and Experience
token limits. The repository available to each model is complete; the shared
CortexWeave index includes every file under `src/**` and no non-source file.

Run the lanes one at a time at the same canonical absolute workspace path. This
preserves the persisted workspace identity and path while preventing concurrent
writers. Baseline runs first so its operator cannot learn from the assisted
outcome. Each model run starts in fresh context with the same model snapshot,
reasoning setting, prompt, tool policy, time limit, and initial repository
state. Record any setting the host cannot pin as a confounder.

## Reproducible failure pair

Identify mutation targets by the exact preimage below, not by a fixed line
number. Abort if an anchor is absent or occurs more than once.

### Task A: create the Experience

In `src/domain/failure.rs`, replace:

```rust
Self::RustCompiler => "rust_compiler",
```

with the undefined identifier:

```rust
Self::RustCompiler => missing_rust_compiler_label,
```

This produces a Rust `E0425` in `FailureDomain::as_str`. Capture the real
structured compiler diagnostic from `cargo check --message-format=json`; do not
derive typed fields from rendered diagnostic prose.

Task A is a controlled evidence-producing sequence rather than a scored model
run:

1. Record the initial nonzero compiler result.
2. Replace `missing_rust_compiler_label` with the still-undefined identifier
   `rust_compiler`, reindex, record a typed successful editor-completion Event,
   and run `cargo check` again. This is the retained, still-failing approach.
3. Replace that expression with the original `"rust_compiler"` literal,
   reindex, record another typed successful editor-completion Event, and run
   `cargo check`.
4. Record the zero-exit structured compiler result, close the debugging
   episode, preview consolidation, and accept only the exact returned episode
   fingerprint and proposal hash.
5. Verify that the Experience is active, `verified_passed`, contains both
   attempts in order, and makes only a verified-after claim.

Every Event carries the Task A session and task IDs. Attempt markers use
`cortexweave.external_tool_completion` version 1 with `tool: "editor"`, a
truthful bounded operation identifier, zero exit status, and no claimed error.
Compiler observations use `cortexweave.rust_compiler_result` version 1 with
actual command exit status and structured diagnostics. Persist the exact
pre/post source, BLAKE3 hashes, model-independent edit record, and raw compiler
stream beside the normalized Event JSON. The editor Event asserts only tool
completion; it does not assert a historical code snapshot or causation.

After cleanly closing CortexWeave, create a consistent SQLite backup with the
SQLite backup API, or checkpoint and truncate the WAL before copying the closed
database. Run `PRAGMA integrity_check` against the backup. Copy the repaired
repository only after the same shutdown boundary. This repository/database pair
is the immutable post-Task-A fork point. Record their hashes and the accepted
Experience ID; never treat a bare live-database copy as a valid fork point.

### Task B: paired repair

For each lane, restore the fork point and in `src/domain/experience.rs` replace:

```rust
Self::StillFailing => "still_failing",
```

with the undefined identifier:

```rust
Self::StillFailing => missing_still_failing_label,
```

Reindex, run the same structured `cargo check`, and record the current failure
under a fresh lane-specific session and task. Normalize that recorded Event and
retain the complete canonical `FailureSignature` returned by CortexWeave.

Before dispatch, assert that:

- the baseline and assisted repository hashes match after Task B injection;
- their database hashes matched before lane-specific session creation;
- the normalized Task B signatures have the same domain and compatible
  components as Task A, while retaining their truthful distinct source paths;
- baseline context reports Experience `not_requested`, selects no Experience,
  and has zero Experience tokens;
- assisted context selects exactly the Task A Experience as
  `historical_supplemental`, reports an active lifecycle and verified outcome,
  and still selects the current Task B source, task, and failure Event ahead of
  it; and
- no Task B Event or model output from one lane exists in the other lane.

If any assertion fails, the pair is invalid and must not be interpreted.

## Model task

Give each fresh model run this exact task, followed by its lane's serialized
context packet:

> Repair the current Rust compiler failure in this CortexWeave checkout. Use
> current repository evidence as authoritative, make the smallest justified
> source change, and verify the outcome with the relevant compiler or tests. Do
> not change generated files, evaluation artifacts, or unrelated code. Report
> what changed and the verification result.

The harness may expose repository inspection, file editing, `cargo check`, and
targeted test tools. It must not expose the other lane, the experiment protocol,
or Task A transcripts. The baseline must not receive the accepted Experience by
another route. The assisted prompt must not characterize the Experience as
advice or current truth beyond CortexWeave's own packet content.

## Measurements

Write append-only raw traces first, then derive one versioned JSON report. For
each lane record:

| Measure | Fixed definition |
| --- | --- |
| Task success | The exact Task B mutation is repaired, `cargo check` exits zero, any model-run targeted tests pass, and no unrelated tracked source is changed. |
| Iterations | Distinct source-edit attempts before the first verified outcome. |
| Tool calls | All model-initiated tool invocations, including failed calls; exclude harness setup and evidence recording. |
| Compiler/test cycles | Completed compiler or test process invocations initiated by the model, reported separately and as a total. |
| Context tokens | `ContextPacket.estimated_tokens` at dispatch. |
| Experience tokens | Sum of `estimated_tokens` for dispatched items whose source type is `experience`. |
| Time to verified outcome | Monotonic elapsed time from model dispatch to the first qualifying zero-exit verification after the repair; report but do not treat as reproducible when host load or caching is uncontrolled. |
| Failed approach avoided | Whether the still-undefined unquoted identifier `still_failing` was attempted. Record true, false, or not applicable with the supporting edit trace. |
| Current evidence displaced | Whether source, active task, or current failure evidence required to diagnose Task B is absent, ordered behind Experience contrary to policy, or lost because of Experience budgeting. |

Also retain model and reasoning identifiers, host and tool versions, source and
binary hashes, database fork hash, lane order, packet JSON, selected Experience
IDs and authority, command exit codes, final diff, and raw monotonic timestamps.
Token counts are CortexWeave packet estimates, not provider billing tokens;
provider-reported prompt and completion tokens may be recorded separately.

## Predeclared interpretation

Interpretation is a separate xhigh pass over sealed raw artifacts.

- **Helped:** assisted succeeds where baseline fails, or both succeed and the
  assisted run avoids the retained failed approach with a strict reduction in
  edit iterations or compiler/test cycles, without displacing current evidence
  or adding unrelated changes.
- **Harmed:** baseline succeeds and assisted fails, assisted requires more edit
  iterations or compiler/test cycles because of the Experience, or the
  Experience is badly selected or inverts current-evidence authority. Bad
  selection or authority inversion is a v0.5 blocker even if the final repair
  succeeds.
- **No material difference:** both lanes have the same success result and no
  predeclared helped or harmed condition is supported. Differences only in tool
  calls, estimated tokens, or wall time are descriptive confounders for this
  single pair.

Do not average unlike measures into a score. Report contradictory signals and
all confounders. A correct null result is acceptable and must be recorded.

## Revision 6 result

Revision 6 completed as a valid pair and receives the predeclared **Helped**
label. Both lanes made the exact repair, avoided the retained unquoted
`still_failing` approach, finished with a clean repository, and passed an
independent offline compiler check. Assisted used two compiler/test cycles
while baseline used three, with no current-evidence displacement or unrelated
change.

The label is intentionally narrow. Baseline's third cycle was a discretionary
targeted test after its first passing compiler result; assisted reached its own
first passing compiler result 3.435 seconds later. Both lanes used one semantic
source edit and 27 total model-initiated tool calls. Repeated Windows execution
and patch-transport failures were preserved in the traces and are not
attributed to Experience.

See `v0.5-real-repository-paired-experiment-result.md` for the sealed controls,
measurements, hashes, contradictory signals, and confounders. This single case
does not authorize tuning retrieval, budgets, authority, or consolidation.

## Abort and contamination rules

Abort without a helped/harmed/null label if the source anchors drift, the
compiler produces multiple or unstructured errors, Task A does not consolidate
from truthful evidence, Task B does not retrieve the intended Experience in the
assisted preflight, the baseline receives Experience content, lane snapshots
differ, a model run has prior conversational state, a lane observes the other's
artifacts, or a tool/model setting changes between runs.

Never tune ranking, budgets, prompts, or the failure pair after seeing a lane
outcome. A revised protocol receives a new version and both lanes are rerun from
a newly sealed fork point.
