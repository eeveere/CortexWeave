# CortexWeave v0.5 Release Boundary Decision

**Status:** Accepted for planning on 2026-08-28 and amended on 2026-08-29.
Implementation remains gated on completion of the v0.4.1 release boundary.

## Decision

CortexWeave v0.5 will ship a **Verified Experience Core**.

The release will prove one narrow capability end to end:

> A bounded development episode can be converted into an immutable,
> evidence-backed experience, and a later session can retrieve that experience
> without receiving the original transcript or an unsupported causal claim.

The release-blocking path is:

```text
typed factual evidence
→ explicit episode
→ normalized failure signature
→ failure / attempts / later verification
→ immutable experience
→ explainable retrieval
→ bounded context inclusion
→ fresh-session reuse experiment
```

Automatic lifecycle management, broad memory generalization, and model-assisted
consolidation are not part of the v0.5 release boundary.

## Why This Boundary

The proposed v0.5 roadmap contains several different research problems:

- episode formation;
- causal interpretation of action and outcome sequences;
- experience representation;
- duplicate and contradiction analysis;
- memory lifecycle and retention;
- pattern generalization;
- adaptive retrieval feedback;
- optional language-model summarization.

Implementing all of them before validating experience reuse would create a
large policy surface around an unproven loop. The first release must establish
whether verified prior experience improves a later coding task while preserving
source authority, workspace isolation, and provenance.

The boundary deliberately optimizes for precision and auditability before
recall or autonomy.

## Baseline

v0.5 assumes the completed v0.4.1 release-blocking path provides:

- the shipped v0.3 workspace, session, task, event, memory, checkpoint,
  working-set, context, and native-harness contracts;
- explicit imported-memory trust review and reviewed supersession;
- deterministic, read-only memory duplicate and structured-claim analysis;
- normalized graph symbols and typed relationship facts;
- durable graph provenance, revisions, and freshness state;
- bounded structural traversal and graph-aware context;
- symbol/path impact analysis;
- deterministic upgrade convergence from the supported migration floor;
- graph-only repair and forced reprojection that preserve compatible chunks,
  embeddings, and source revisions;
- coherent graph reads during repair, shared CLI/MCP workspace resolution, and
  actionable repair diagnostics;
- thin CLI and MCP adapters over `CortexWeaveService`.

v0.5 does **not** assume that optional v0.4 work shipped. In particular, the
release may not assume:

- Git working-tree or base-diff inspection;
- parsed compiler or test diagnostic locations;
- diagnostic-to-symbol mapping;
- graph-driven working-set activation;
- a high-frequency external event streaming transport;
- a durable action-to-outcome relationship model;
- a dedicated coding-agent harness.

If any optional v0.4 capability is present, v0.5 may consume it through an
explicit capability check. The core experience pipeline must work without it.

## Required Vertical Slice

### Typed Evidence Input

The existing `CortexEvent` envelope remains an append-only factual domain, but
v0.5 must define and validate the payload contracts required by the experience
pipeline. At minimum:

- external tool completion;
- Rust compiler result;
- Cargo test result;
- source-change observation;
- explicit episode start and end;
- explicit task/session provenance.

Unknown and legacy event payloads remain inspectable events. They do not become
consolidation evidence until a registered extractor can validate their schema.

### Explicit Episodes

The initial release uses explicit episode control through the application
facade. An episode:

- belongs to exactly one workspace;
- belongs to exactly one session;
- may belong to one task from that workspace and session;
- has one type and one lifecycle status;
- contains an ordered set of event memberships;
- may reference paths and graph symbols as provenance;
- closes explicitly before consolidation.

One event may have at most one primary episode membership. Other experiences
may still cite that event as evidence. This prevents automatic grouping from
double-counting one event while allowing evidence reuse.

An episode never spans workspaces or sessions. Cross-session learning occurs
through the resulting experience, not by creating a cross-session episode.

### Failure Signatures

v0.5 initially normalizes only:

- Rust compiler failures emitted by supported typed payloads;
- Cargo test failures emitted by supported typed payloads;
- generic tool failures with a stable tool name, operation, error class, and
  exit status when available.

A signature is workspace-scoped evidence, not a global truth. It records the
normalizer identity and version. Normalization may remove timestamps, process
IDs, temporary paths, UUIDs, and source line movement only when the remaining
fields still distinguish materially different failures.

Diagnostic-to-symbol mapping is capability-gated. A signature may include a
symbol only when the event supplied one explicitly or a current v0.4 structural
service can resolve it from deterministic location evidence. It must not infer
a symbol from semantic similarity.

### Experience Records

`Experience` is a first-class domain separate from `MemoryRecord`,
`CortexEvent`, and the code graph.

The initial experience contains:

- workspace, source episode, session, and optional task provenance;
- a normalized problem or failure signature;
- ordered attempts represented by evidence references;
- an outcome;
- a verification assessment;
- related path and symbol snapshots;
- bounded evidence links;
- a deterministic extractor identity and version;
- an immutable created-at timestamp.

The experience row and the evidence used to construct it are immutable. A later
conflict creates an assessment, dispute, superseding experience, or other
append-only relation; it does not silently rewrite the historical experience.

Explicit memories remain the place for human-authorized decisions, facts,
notes, failures, and solutions. v0.5 does not add every proposed experience
category to `MemoryKind`.

### Causal Humility

Temporal order is not proof of causation.

The deterministic consolidator may state:

```text
failure observed
→ these attempts occurred in the same episode
→ verification later succeeded
```

It may not automatically state:

```text
change X caused the success
```

Automatic evidence relations use terms such as:

- `observed_in`;
- `attempted_during`;
- `changed_during`;
- `verified_after`;
- `refuted_by`;
- `related_code`.

`resolved_by` requires an explicit, provenance-bearing assertion plus matching
verification. `caused_by` is outside the automatic v0.5 pipeline.

If unrelated changes, ambiguous scope, missing verification, or conflicting
results prevent a supported conclusion, the experience outcome is
`Inconclusive` or the candidate is rejected.

### Verification-Aware Outcomes

The initial outcome set is:

- `Success`;
- `Failure`;
- `PartialSuccess`;
- `Inconclusive`;
- `Abandoned`.

`Success` requires a registered deterministic verifier or explicit user
acceptance. Agent completion, inactivity, episode closure, command invocation,
and exit code alone are not universally equivalent to successful verification.

The verifier records:

- the asserted verification kind;
- the exact evidence event;
- the subject or scope that was verified;
- the rule and rule version;
- whether later conflicting evidence is known.

### Evidence Strength

v0.5 does not store an unexplained floating-point confidence as truth.

It stores a structured assessment containing:

- a bounded strength level;
- one or more evidence bases;
- the deterministic rule and version;
- reasons visible to callers.

A numeric ranking contribution may be computed from those components, but the
components remain authoritative and explainable.

### Deterministic Consolidation

The first consolidator is synchronous or manually invoked. It:

- accepts one closed episode;
- validates every evidence reference;
- orders evidence deterministically;
- extracts a supported failure/attempt/verification sequence;
- produces either one deterministic proposal or a typed no-result reason;
- computes a stable consolidation fingerprint;
- persists an accepted experience idempotently.

The same episode, extractor version, and evidence set must produce the same
canonical result. Repeating consolidation must not produce duplicate
experiences.

No background worker, idle scheduler, or automatic retention policy is needed
to prove this release.

### Experience Retrieval and Explanation

The application facade exposes transport-neutral operations equivalent to:

- `experience_search`;
- `experience_get`;
- `experience_explain`;
- explicit episode creation, event association, closure, and consolidation.

Search initially combines deterministic failure-signature matching, lexical
matching, workspace scope, outcome, verification strength, and optional exact
path/symbol filters. Semantic experience embeddings are not required for the
release-blocking path.

Every result explains:

- why it matched;
- which failure signature, path, or symbol contributed;
- the outcome and verification basis;
- the evidence links;
- the source episode and extractor version;
- any stale or unresolved structural provenance.

### Context Integration

Experience becomes a distinct context source type with a separately bounded
budget. It does not masquerade as current source or ordinary memory.

Current source and current deterministic diagnostics remain more authoritative
for present-state questions. Historical experience may suggest a previously
useful approach, but it cannot override current code, active decisions, or
verified current observations.

Experience enters context automatically only when:

- the request has an active failure signature or explicitly enables experience;
- the experience belongs to the current workspace;
- the experience is not disputed or superseded;
- its verification and scope pass the deterministic eligibility policy;
- the category budget remains available.

The packet explanation must identify the experience-specific selection reason.

## Persistence Boundary

SQLite continues to own transaction boundaries.

The minimal durable additions are:

- episodes;
- event-to-episode membership;
- experiences;
- ordered experience attempts or actions;
- typed evidence links;
- verification assessments;
- consolidation fingerprints;
- optional append-only experience assessments or disputes.

Composite workspace ownership is enforced in SQLite, not only in service
validation. Cross-workspace evidence links, episode memberships, and related
graph references must fail at the persistence boundary.

Evidence links to mutable or derived code state carry a snapshot containing the
workspace content revision, graph revision when applicable, stable logical key,
path, source hash when available, and source range. A graph node or chunk ID
alone is not sufficient historical evidence because derived rows can be
reconciled or deleted.

Raw events and explicit memories are not copied into experience payloads. The
experience stores references plus the minimum immutable snapshot required to
explain historical meaning after current source changes.

## Embedding Boundary

Experience embeddings are not a v0.5 release blocker.

If they are added after the deterministic retrieval baseline, each record must
store provider/model identity, dimension, content hash, and embedding pipeline
version. Search must select one compatible vector space and must never compare
or silently mix incompatible models or dimensions.

An experience text change creates a new immutable summary or version and a new
compatible embedding; it does not mutate the meaning of an existing experience
without provenance.

## Adapter Boundary

Core and application code remain independent of MCP, CLI, JSON-RPC, stdio, and
any future dedicated harness.

The native application facade is implemented first. CLI and MCP exposure may
follow only after the service contract and full-cycle integration test are
green. Adapters perform workspace resolution, argument parsing, response
bounding, and serialization. They do not form episodes, infer outcomes, rank
experiences, or validate evidence independently.

The v0.5 acceptance experiment uses a deterministic simulator or fixture
driver. A production coding-agent harness is not a prerequisite.

## Release Blockers

v0.5 is not complete until all of the following are proven:

- typed evidence validation rejects malformed and unsupported payloads;
- explicit episode lifecycle and membership are workspace-safe;
- the initial failure normalizers distinguish labeled same/different failures;
- deterministic consolidation is idempotent;
- every experience claim is traceable to existing evidence;
- automatic consolidation makes no unsupported causal claim;
- current source remains authoritative over historical experience;
- disputed or superseded experience is excluded from ordinary context;
- cross-session retrieval works without transcript carryover;
- cross-workspace evidence and retrieval leakage are rejected;
- experience context is bounded and explainable;
- existing v0.1 through v0.4.1 quality gates remain green;
- the paired fresh-session reuse experiment is recorded with its result.

## Deferred Work

The following are explicitly outside the v0.5 release boundary:

- broad automatic episode grouping;
- episodes spanning sessions or tasks;
- semantic duplicate merging;
- automatic memory merges;
- general natural-language contradiction reasoning;
- automatic pattern or anti-pattern promotion;
- automatic lesson generalization;
- reuse-driven confidence updates;
- negative feedback loops from task outcomes;
- automatic importance decay;
- automatic archival or hard deletion;
- workspace-to-global promotion;
- graph-driven experience generalization;
- a background consolidation scheduler and worker pool;
- a live model-backed consolidator;
- unbounded or automatic LLM summarization;
- autonomous planning or tool execution;
- a dedicated CortexWeave coding-agent harness.

These may be evaluated only after the release experiment produces trustworthy
experience data and baseline precision metrics.

## Evaluation Contract

### Deterministic Fixture

Session A records:

```text
compiler or test failure
→ attempted change A
→ verification still fails
→ attempted change B
→ verification succeeds
→ episode closes
→ consolidation runs
```

The resulting experience must expose the failure signature, both attempts, the
verified later outcome, exact evidence, and a causal-humility explanation.

Session B starts without Session A's transcript, observes a labeled similar
failure, and searches for experience. The expected experience must appear in
the bounded result and context packet for the documented selection reason.

### Negative Controls

The evaluation also includes:

- a superficially similar but materially different failure;
- the same failure text in another workspace;
- a later success after unrelated changes;
- a closed episode with no verification;
- a success followed by a later matching failure;
- a source symbol renamed or deleted after the experience was created;
- repeated consolidation of the same episode;
- stale graph provenance;
- malformed legacy event payloads.

### Initial Metrics

The release records:

- failure-signature precision on labeled pairs;
- top-k experience retrieval precision and recall;
- unsupported-claim count;
- false-causal-claim count;
- duplicate-experience count after repeated consolidation;
- cross-workspace leakage count;
- experience context tokens and category utilization;
- resolution iterations, tool calls, verification cycles, and context tokens in
  the paired task experiment.

The release does not claim generalized performance improvement from one paired
experiment. It establishes a reproducible baseline and reports whether the
experience-assisted run helped, harmed, or made no material difference.

## Stop Conditions

Implementation pauses for an architecture review if:

- required evidence cannot be represented without copying or mutating raw
  evidence;
- reliable episode membership requires a production harness;
- success cannot be scoped to the failure subject;
- the extractor must infer causality from temporal order;
- historical code evidence cannot survive ordinary v0.4 graph reconciliation;
- experience ranking needs incompatible vector spaces;
- automatic context inclusion measurably displaces required current evidence;
- the proposed schema collapses events, memories, experiences, and graph state
  into one polymorphic domain.

## Consequences

This boundary produces a smaller v0.5 than the original broad proposal, but it
preserves the proposal's central research question. It creates real data for
later decisions about episode inference, consolidation scheduling, retention,
patterns, and model assistance.

The dedicated harness remains intentionally later. When it begins, it can use
verified source structure and verified prior experience rather than forcing the
harness to invent those capabilities inside its own control loop.
