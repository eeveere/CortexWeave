# v0.5 Checkpoint 70: Deterministic Consolidation Algorithm Design

**Date:** 2026-08-30

**Scope:** Phase 5 algorithm design on GPT-5.6 Sol/xhigh

## Result

The Phase 5 deterministic failure-to-verification algorithm is specified for
implementation. No consolidator, facade mutation, or production Experience
write path was added during this design segment. The next step is the planned
Terra/high implementation.

The design is deliberately conservative. It produces no Experience when an
event could change attempt boundaries or outcome meaning but cannot be decoded,
when verification scope is ambiguous, or when a terminal state is not proven.
It never skips uncertain material evidence merely to obtain a cleaner result.

## Public Application Shape

The native surface has two operations:

```text
preview_experience(request) -> Proposal | NoResult
accept_experience(request, expected_fingerprint, expected_proposal_hash)
    -> Accepted | NoResult
```

`ConsolidationRequest` contains only `workspace_id`, `episode_id`, and
`expected_episode_version`. Callers cannot select an extractor by string. The
built-in identity is `cortexweave.failure_to_verification` version `1`.
Generated IDs, request keys, and display timestamps are never request or hash
identity.

Preview is read-only. Acceptance reruns the built-in preview, requires exact
caller-supplied fingerprint and proposal hash, and passes only the internally
materialized record to the crate-private aggregate persistence primitive.
There is no API that accepts an `ExperienceRecord` from a caller.

The result is a tagged union:

```text
ConsolidationPreview
├── Proposal { proposal, disposition }
└── NoResult { reason, diagnostics }

ProposalDisposition
├── Automatic
└── ReviewRequired { reasons }
```

Phase 5 acceptance accepts only `Automatic`. Review-required proposals remain
inspectable but read-only until a later authenticated review operation exists.

## Loaded Input

The loader obtains one coherent ordered input:

- the episode and exact terminal version;
- all primary memberships ordered by membership ordinal;
- each immutable event envelope, type, and payload;
- exact workspace/session/task equality for every event; and
- current source/graph state only for separately validated snapshot capture.

Missing rows and impossible ordinal/provenance states are corruption errors,
not normal no-results. The expected version mismatch, an open or invalid
episode, an empty episode, or a hard evidence limit is a typed no-result.

Only `Closed` episodes can produce automatically acceptable proposals.
`Abandoned` episodes may preview an `Abandoned` proposal when the supported
prefix contains an initial failure and at least one attempt, but the proposal
is review-required and is not persisted in Phase 5.

## Material Event Classes

Classification uses the decoded observation, never event type alone:

| Decoded observation | Material role |
|---|---|
| Rust compiler result | failure or scoped verification result |
| Cargo test result | failure or scoped verification result |
| registered generic verifier result | failure or scoped verification result |
| user acceptance | scoped positive result requiring review |
| source-change observation | attempt change |
| ordinary external-tool completion | attempt/tool action, never verification |

`TaskCompleted`, process exit zero on an ordinary tool, an agent-authored
message, and an unregistered generic verifier are not task or fix success.

Compiler, test, user-acceptance, source-change, and external-tool-finished
events are material-capable. If any such member has an invalid, legacy,
unknown, or unavailable payload contract, extraction stops with a typed
no-result. Nonmaterial episode members may be excluded with bounded reason
codes; they do not create or close an attempt.

## Deterministic State Machine

The extractor scans membership ordinals once and constructs alternating
change and result runs:

```text
Prelude
  -> InitialFailure
  -> AttemptChanges+
  -> ResultBatch+
  -> (AttemptChanges+ -> ResultBatch+)*
  -> TerminalFrontier
```

### 1. Initial failure

The initial failure is the first mechanically failed decoded verifier result
that the registered normalizer can normalize. Passed results before it are
excluded prelude. A failed result that cannot be normalized is not skipped in
favor of a later convenient failure; it returns `NoSupportedFailure` with the
normalizer diagnostic.

Before the first attempt, an exact repeat of the initial normalized key is
supporting evidence. A different supported failure or a positive result before
any attempt makes the initial state ambiguous and returns
`AmbiguousInitialFailure`.

### 2. Attempt boundary

One attempt is a maximal nonempty run of decoded source changes and ordinary
external-tool completions. Consecutive edits/tool actions are one associated
attempt because no supported result distinguishes their effects. The attempt
owns each change evidence ordinal exactly once.

The first subsequent material result is the attempt's
`following_verification`. A result cannot be skipped because its scope or
content is inconvenient. A new change run starts the next attempt. A closed
episode with a pending change run and no following result returns
`NoVerificationEvidence`. An abandoned episode may retain that last attempt as
`Inconclusive` in its read-only proposal.

### 3. Attempt result

The first following result is classified as:

- `StillFailing` when its normalized failure key equals the initial key;
- `VerificationChangedFailure` when it is a different normalized failure from
  the same verifier family and exact subject;
- `VerificationPassed` when a registered positive verifier covers the exact
  initial verifier family and subject; or
- `Inconclusive` only for the unfinished final attempt of an abandoned
  read-only proposal.

A different target, subject kind, verifier family, or generic rule is not a
changed failure and is not proof of a pass. It returns
`AmbiguousVerificationScope` for the pending attempt.

Attempt results are historical sequence facts. Their result events remain
auditable through exact evidence links, but they are not copied into the
Experience's terminal verification assessment unless the attempt is the final
attempt. This separation is required for the ordinary sequence
`failed -> attempt -> still failed -> attempt -> passed` to produce `Success`
without mislabeling the earlier failure as a conflicting terminal result.

### 4. Terminal frontier

The final attempt's complete consecutive result batch is the terminal
frontier. Its eligible results become ordered
`ExperienceVerificationObservation` values. Earlier attempts retain their
result enum and evidence link but do not contribute terminal observations.

Two opposing results for the same exact subject and rule in one terminal
frontier are conflicting; order does not silently turn a nondeterministic run
into truth. Repeated results with the same status may remain separate ordered
observations and can support repeated-evidence strength.

## Verifier Identity and Exact Scope

V1 uses no inferred scope lattice. Compatibility is exact:

```text
(verifier family or registered rule ID/version,
 subject kind,
 subject value)
```

Rust compiler and Cargo test results receive built-in rule IDs and versions.
Generic results require the already registered exact rule, tool, operation,
allowed subject kind, reported result, and matching process outcome. A
workspace/package/target pass is not assumed to cover a narrower failure, and
a test pass is not assumed to prove a compiler failure.

The initial failure signature's canonical `subject_kind` and `subject_value`
components define its subject. A registered-tool failure also requires its
exact canonical rule identity. Any future scope containment requires a new
versioned deterministic rule; it is not guessed from names or graph proximity.

User acceptance can form an `ExplicitlyAccepted` terminal observation only for
an exact subject. Because the current event contract reports but does not
authenticate the actor, any proposal relying on it is `ReviewRequired` and
cannot be accepted automatically in Phase 5.

## Outcome Rules

Outcome uses only the terminal frontier:

- `Success`: at least one positive observation compatible with the initial
  failure, and no failed terminal observation in the eligible verifier family;
- `Failure`: at least one failed observation compatible with the initial
  subject, and no positive terminal observation in that family;
- `PartialSuccess`: at least one positive and one failed observation for
  distinct exact subjects in the eligible verifier family, with at least one
  observation covering the initial subject;
- same-subject positive/failed conflict: `ConflictingResults` no-result;
- no observation covering the initial subject: `AmbiguousVerificationScope`
  no-result; and
- missing/unsupported terminal evidence: typed no-result, not an automatically
  persisted `Inconclusive` Experience.

`Inconclusive` remains a valid historical/manual domain outcome but is not an
automatic Phase 5 acceptance result. `Abandoned` is preview-only in this phase.

## Cargo Execution Proof

A zero-exit Cargo test report is positive evidence only when the typed payload
reports a nonzero executed-test count. Zero executed tests returns
`EmptyVerificationRun`; it cannot prove success. Phase 5 implementation must
extend the still-unreleased Cargo-test v1 contract and its fixtures with this
bounded count before using Cargo passes.

The count proves that the declared run was nonempty; it does not prove that a
broad or filtered run covered another subject. Exact scope compatibility still
applies.

## Evidence Relations

Material evidence is emitted in membership order:

- the selected initial event is `initial_failure`;
- each attempt action is `attempt_change`;
- the first result after each attempt is `attempt_verification`;
- additional final-frontier results are `terminal_verification`; and
- exact repeats or useful non-outcome facts may be `supporting`.

Unrelated/nonmaterial events are excluded with reason codes rather than
receiving a relation that implies semantic use. One event receives at most one
relation. Every attempt change and following-verification relation has exactly
one attempt owner.

## Evidence Strength

Every automatic conclusive proposal contains `TemporalAssociation` and
`DeterministicVerifier` bases and is at least `Moderate`.

`Strong` additionally requires repeated, distinct terminal event evidence for
every outcome-bearing subject with the same rule and status. It adds
`RepeatedDeterministicEvidence`. Multiple edits, lexical similarity, graph
proximity, or elapsed time never increase strength. A captured graph snapshot
may add `StructuralAssociation` but does not raise the strength by itself.

An acceptance-based read-only proposal uses `ExplicitUserAcceptance` and never
uses `ExplicitHarnessAssertion`; v1 has no authenticated harness-assertion
contract.

## Historical Snapshot Rule

For each source-change attempt, automatic acceptance requires an immutable
snapshot or an explicit determination that no content can exist (for example,
a removal). Snapshot capture is allowed only when current durable source state
exactly matches the reported workspace revision, document revision, path, and
document BLAKE3 hash. Full source content must fit the hard snapshot bound and
must hash to the stored document hash.

The Phase 5 implementation must bring the Phase 4 snapshot shape into exact
alignment with D071. A code snapshot needs:

- source evidence event ID and normalized historical path;
- workspace content revision;
- document content revision and document hash;
- bounded source content;
- optional chunk stable key/hash, symbol logical key/label, and source range.

A graph snapshot is optional enrichment. It is captured only from a coherent
graph at the same workspace/document revision and records graph revision,
schema/state, analyzer/structure identity, node stable key/type, and resolution
provenance. Missing graph evidence does not block an otherwise explainable
code snapshot and never causes a symbol to be inferred.

If a source change cannot be snapshotted without reading a newer/different
state, preview may return a proposal marked `ReviewRequired` with
`HistoricalSnapshotUnavailable`; automatic acceptance refuses it. It never
copies current content while labeling it historical.

## Canonical Input Fingerprint

`consolidation_fingerprint` is lowercase BLAKE3 over:

```text
"cortexweave.consolidation-input.v1" || 0x00 || canonical_json(input_identity)
```

The identity contains:

- workspace ID;
- episode ID, exact scope, creator, terminal status, and terminal version;
- every membership ordinal, event ID, event type, and canonical payload hash in
  membership order;
- built-in extractor ID/version;
- the complete sorted decoder-contract, normalizer, and verifier-rule identity
  catalogs used by the extractor; and
- summary renderer and canonicalization version.

Each payload hash is lowercase BLAKE3 over:

```text
"cortexweave.event-payload.v1" || 0x00 || canonical_json(payload)
```

Canonical JSON v1 recursively sorts object keys by UTF-8 byte order, preserves
array order, writes strings with the `serde_json` escaping rules, and writes
the semantic `serde_json::Number` using its deterministic shortest serializer.
It does not claim to preserve unavailable original number lexemes. Null and
booleans use their JSON literals, with no insignificant whitespace.

All episode members enter the input identity, including excluded nonmaterial
events. Generated IDs, event/episode display timestamps, association times,
request keys, diagnostics prose, and current graph UUIDs are excluded.

## Material Proposal Hash

`proposal_hash` is lowercase BLAKE3 over:

```text
"cortexweave.experience-proposal.v1" || 0x00 || canonical_json(material)
```

Material contains the canonical failure signature, ordered attempts without
generated IDs, outcome, terminal verification, strength, immutable snapshots,
ordered evidence links, deterministic summary, extractor identity/version,
and renderer version. It excludes the Experience/attempt UUIDs, creation time,
fingerprint itself, proposal hash itself, diagnostics prose, disposition, and
excluded-event display details.

Golden tests must cover object-key order, array order, all JSON number storage
classes, escapes, Unicode keys, `-0.0`, domain separation, and one-field changes
to every input/material category.

## Transactional Acceptance

The persistence transaction receives only an internally materialized record,
the expected episode version, and exact input event identities. In one SQLite
transaction it:

1. verifies the eligible terminal episode and exact scope/version;
2. re-reads ordered membership and event type/payload identity;
3. verifies every cited event and relation;
4. checks the workspace fingerprint uniqueness;
5. returns the existing aggregate only when proposal hashes match;
6. otherwise inserts the complete Experience aggregate and FTS row; and
7. commits without updating events, episodes, memories, source, or graph.

The v0.5 migration must make event rows update-immutable, matching their
application-level append-only contract. Terminal episode membership is already
immutable. SQLite uniqueness, not a process mutex, owns retry/concurrency
convergence. Breakpoint 6 remains responsible for the adversarial concurrent
proof.

## Typed No-Result Taxonomy

The initial enum is bounded and machine-readable:

```text
EpisodeNotClosed
EpisodeIneligible
StaleEpisodeVersion
EpisodeEmpty
EvidenceLimitExceeded
UnsupportedPayloadContract
InvalidPayloadContract
NoSupportedFailure
AmbiguousInitialFailure
NoAttemptEvidence
NoVerificationEvidence
AmbiguousVerificationScope
ConflictingResults
EmptyVerificationRun
FingerprintMismatch
ProposalHashMismatch
ReviewRequired
```

Each result carries structured fields such as expected/actual versions,
membership ordinal, event ID, contract/version, attempt ordinal, or subject.
Human diagnostic text is bounded display material and never identity.

`NotFound`, serialization/storage failure, broken foreign-key provenance, and
impossible persisted ordinals remain errors because they indicate missing
requested state or corruption rather than insufficient experience evidence.

## Causal-Humility Validator

Before preview returns a proposal, validation proves:

- all material fields trace to an exact event or validated snapshot;
- attempt ordering and ownership are complete;
- terminal observations come only from the final result frontier;
- scope/rule compatibility supports the chosen outcome;
- evidence strength follows the fixed rules above;
- the summary exactly matches the deterministic renderer; and
- no relation, reason code, or summary text asserts `caused`, `fixed by`,
  `necessary`, `resolved by`, or current-state validity.

The allowed claim is: an associated attempt was followed by an observed scoped
result. Prior verification never becomes proof of current state.

## Required Implementation Corrections

Terra/high must make these corrections before enabling acceptance:

1. Treat `ExperienceVerification.observations` as terminal observations only.
   Repository validation must not require earlier conclusive attempt results to
   appear in that terminal set; it validates their exact evidence relation,
   while the consolidator validates decoded result meaning.
2. Extend Cargo-test v1 evidence with a bounded executed-test count and reject a
   zero-execution pass.
3. Expand code/graph snapshot types and `0008` columns to the D071 historical
   identity, including source-event linkage and workspace revision.
4. Expose stable identity catalogs from decoders, normalizers, and verifier
   rules for fingerprint construction.
5. Add built-in versioned verifier identities for Rust compiler and Cargo test
   results rather than inventing rule strings at persistence time.
6. Add event update immutability and transaction-time episode/event identity
   revalidation.

## Implementation Test Matrix

At minimum, Phase 5 implementation tests:

- one edit followed by exact scoped pass -> `Success`;
- failure, edit, same failure, edit, pass -> two attempts and `Success`;
- exact repeated failure -> `StillFailing`;
- same subject with a different normalized failure ->
  `VerificationChangedFailure`;
- pass and failure on distinct terminal subjects -> `PartialSuccess`;
- opposing terminal results on one subject -> `ConflictingResults`;
- broad or different-target verification -> `AmbiguousVerificationScope`;
- zero executed tests -> `EmptyVerificationRun`;
- ordinary zero-exit command and `TaskCompleted` -> no verification;
- unregistered generic verifier -> typed no-result;
- unsupported material payload -> typed no-result with exact ordinal;
- unrelated events do not change segmentation but do enter the fingerprint;
- pending closed-episode attempt -> `NoVerificationEvidence`;
- abandoned pending attempt -> read-only `Abandoned` proposal;
- snapshot revision/hash drift -> review-required, never mislabeled history;
- preview is mutation-free;
- acceptance recomputes and matches both hashes;
- exact repeat returns the existing aggregate; and
- stale version/hash mismatch writes nothing.

Breakpoint 5 will separately attack the language and epistemic behavior. The
concurrency/restart/rollback proof remains Breakpoint 6.
