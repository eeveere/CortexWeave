# v0.5 Checkpoint 71: Deterministic Consolidation Implementation

**Date:** 2026-08-30

**Scope:** Phase 5 implementation on GPT-5.6 Terra/high

## Result

The native application now exposes deterministic `preview_experience` and
`accept_experience` operations.  The only acceptance authority is an episode
ID/version plus the preview's exact fingerprint and proposal hash; callers
cannot provide an `ExperienceRecord` for storage.

The built-in `cortexweave.failure_to_verification` v1 extractor loads the
ordered terminal episode membership, requires exact session/task scope, decodes
typed evidence, normalizes the first supported failure, groups repair actions,
and requires a compatible deterministic verifier result.  It returns typed
no-result diagnostics for stale, incomplete, unsupported, invalid, ambiguous,
or empty-test-run inputs rather than guessing.

Acceptance reruns preview and checks both hashes.  Its aggregate write occurs
in a SQLite transaction that rechecks the episode version; episode membership
is versioned and events are now immutable, preserving the previewed input
frontier.  Fingerprint inputs include member payload hashes and the complete
decoder, normalizer, verifier-rule, extractor, renderer, and canonicalizer
identity catalogs.  Proposal hashes exclude generated IDs and timestamps.

Cargo test evidence v1 now carries a bounded `executed_test_count`: a zero-exit
report with no executed tests is a typed `empty_verification_run`, never a
successful verification.

Source-change attempts are deliberately review-required in this increment.
The record remains inspectable but cannot be auto-accepted until a validated
historical content snapshot can be captured; the implementation never copies
current workspace content and calls it historical.  Ordinary tool-action
attempts can be automatically accepted when all deterministic checks pass.
