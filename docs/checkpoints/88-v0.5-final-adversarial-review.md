# v0.5 Checkpoint 88: Final Adversarial Review

**Date:** 2026-09-01

**Scope:** Breakpoint 13 on GPT-5.6 Sol/ultra

## Result

The breakpoint review is complete, but the v0.5 release gate does not pass.
Eight blocker groups remain for Final Hardening. They are release-contract and
historical-truth defects, not evidence that the deterministic Experience design
should be abandoned. Six material corrections are now frozen in
[`docs/decisions.md`](../decisions.md) as D098-D103.

No production implementation was changed in this breakpoint. The review stops
at the planned model boundary before Final Hardening.

## v0.5 Blockers

### B1. Accepted historical aggregates are neither fully immutable nor sealed

`migrations/0008_experience_domain.sql` rejects updates to Experiences, Events,
and the core Experience child tables, but it does not reject their narrow
deletion. `migrations/0010_experience_assessment_immutability.sql` adds
workspace-aware delete guards only for episode membership, assessments, and
assessment evidence. An unassessed Experience can therefore be deleted with its
children; individual attempts, evidence links, verifications, snapshots, and
strength bases can also be removed. Core child rows can be inserted after the
aggregate was accepted, changing its historical meaning.

This is reachable through the public SQLite pool and contradicts the documented
SQLite-level immutability boundary. Foreign-key restrictions protect referenced
Events and some assessed records incidentally, but that partial protection is
not an aggregate seal.

Final Hardening must:

- reject narrow deletion of Events, Experiences, and every historical child
  while the workspace exists;
- reject core component insertion after an Experience is sealed;
- seal the complete aggregate in the acceptance transaction and migrate
  existing aggregates as sealed;
- preserve intentional full-workspace cascade deletion; and
- prove all four properties with direct-SQL regression tests.

### B2. Coarse failure classes are promoted to exact identity

Rust failures other than `E0308` can normalize from diagnostic code, subject,
and path alone. Cargo-test failures can normalize from a test name or assertion
class, and a registered `cargo.check` failure can normalize from rule, subject,
and a generic `nonzero` class. Different failures at the same scope can
therefore receive the same key.

That equality is nevertheless used for `StillFailing`, exact Experience search,
and exact recurrence. The five-pair quality review did not include adversarial
same-scope/different-error pairs, so its reported precision did not exercise
this false-exactness case.

Final Hardening must distinguish exact-capable signatures from compatible-only
classes. Only a code/rule-specific structured discriminator may support exact
equality; free-form prose remains excluded. Same-file/same-code, same-test, and
same-verifier/different-failure pairs become release fixtures.

### B3. “Later recurrence” trusts a caller-controlled timestamp

Dispute proposals compare `event.created_at` with
`experience.created_at`. `CortexEvent.created_at` is caller supplied, and
`record_event` persists it unchanged. A caller can record an Event before an
Experience while assigning the Event a future timestamp, then receive a
proposal that says the failure recurred later.

The proposal is read-only, which limits the effect, but the proposal's evidence
claim and D090's “recorded strictly after” statement are still unsupported.

Final Hardening must use a durable SQLite-owned Event-ingress/Experience-
acceptance order and store the acceptance frontier transactionally. Migrated
history without provable order must produce no automatic recurrence proposal.

### B4. Experience context applies authority after destructive bounds

Context asks general Experience search for only its candidate ceiling (eight by
default). Search orders by additive retrieval score, then newest creation time,
and truncates before context applies verification, evidence-strength, and
outcome authority. Exact-signature candidate sourcing is itself capped to the
newest records before that policy runs.

A concrete counterexample is nine equal exact matches: eight newer moderate
failures can remove an older strong verified success before context sees it.
Among retained exact peers, a 40-point lexical bonus can also make a moderate
`verified_failed` failure outrank a strong `verified_passed` success. Both
outcomes contradict D087; creation time is not an authority signal.

Final Hardening must use one lexicographic authority tuple before every bound,
including storage candidate sourcing. Exact/compatible specificity,
verification status, evidence strength, and outcome precede optional lexical
relevance; stable identity is the final tie-breaker.

### B5. Assessment retries, lifecycle projection, and history output are unbounded

A reviewed assessment has bounded evidence per row but no caller idempotency
key or bound on history length. Every retry receives a new UUID and appends a
new immutable row. Lifecycle-dependent search loads every assessment for every
candidate, and the repository then performs one evidence query per assessment.
Context repeats the detail load. Detail/explanation and history operations
return the complete vector, while MCP serializes it into both text and
structured content.

Repeated valid reviews can therefore manufacture duplicate historical entries,
make normal search/context work grow without bound, and produce an unbounded
transport response.

Final Hardening must add transactional assessment request identity, an indexed
bounded lifecycle projection, stable maximum-sized history pages, bounded
assessment detail, and a bounded overlap query for context deduplication. CLI
and MCP must expose the same application paging contract.

### B6. The release artifact still identifies itself as v0.4.1

The README now describes v0.5, but `Cargo.toml`, the root package entry in
`Cargo.lock`, CLI version output, MCP `serverInfo`, and their tests still report
`0.4.1`. A v0.5 binary cannot ship under the previous release identity.

Final Hardening must move the package and all asserted public version surfaces
to `0.5.0` from the single Cargo package version.

### B7. Release documentation implies review-required proposals are acceptable

The application correctly returns `ReviewRequired` before checking acceptance
hashes, and the accepted architecture says those proposals remain read-only in
v0.5. The CLI guide nevertheless tells users to consolidate any preview that
contains a proposal; the verified-experience guide and MCP description do not
state the disposition restriction.

Final Hardening must say consistently that only an `automatic` proposal can be
accepted in v0.5. A review-required proposal is inspectable and has no bypass or
reviewed-acceptance API in this release.

### B8. Context and Event projections lack service-level hard ceilings

MCP caps a requested context budget at 65,536 tokens, but CLI accepts an
unrestricted `usize`, and the application service validates ownership rather
than an absolute context ceiling. Raw Event JSON is stored without a payload
limit and is rendered verbatim as an Event candidate; a sufficiently large
caller budget can therefore produce an arbitrarily large native or CLI packet.
Path and language scope arrays are likewise uncapped and are scanned for every
candidate.

This conflicts with the plan's requirement that context tokens, related paths,
and projections have configuration bounds plus hard ceilings. A caller budget
must select within a supported range rather than disable the range.

Final Hardening must enforce application-level context token and per-item byte
ceilings for semantic and resume paths, bound/normalize/deduplicate scope arrays,
and retain the same or tighter adapter limits. Raw legacy Events may remain
faithful stored provenance, but oversized payloads are ineligible for typed
evidence and their context rendering is explicitly bounded.

## v0.5 Hardening

These findings do not independently invalidate the architecture, but they are
accepted for the Final Hardening pass:

1. Context currently can search an active Experience, observe a newly negative
   lifecycle on the detail reread, then emit the stale lifecycle from the search
   hit. Use the fresh detail eligibility at minimum; D101 requires one
   internally consistent admission snapshot.
2. Path validation has three subtly different implementations. The evidence
   decoder rejects backslashes and `.` segments, while public signature and
   repository validation can accept values such as `..\\outside.rs`. Replace
   them with one strict normalized slash-relative validator.
3. Documentation says signatures exclude secrets, but bounded producer-owned
   subject, target, test, and type identifiers are not secret-scanned. State the
   producer trust requirement and claim only the fields actually excluded.
4. `consolidation_acceptances` counts acceptance attempts, including typed
   no-results. Split attempts, accepted results, and no-result outcomes so the
   metric name cannot imply persisted Experience rows.
5. `doctor` converts a workspace-list storage error into an empty healthy list.
   Preserve that error as a failed check so watcher, resolution, and graph
   health cannot be reported from fabricated emptiness.
6. Add successful CLI and MCP round trips for preview/automatic acceptance,
   explain/paged history, reviewed assessment idempotency, and dispute proposal
   ordering. Existing adapter tests cover discovery and selected rejection paths
   more deeply than the successful v0.5 lifecycle.

## Post-v0.5 Research

- General secret/high-entropy detection for arbitrary stable identity fields is
  deferred. v0.5 can enforce explicit field allowlists and accurate claims; a
  heuristic sanitizer needs separate precision evaluation.
- Broad Experience utility, learned ranking, semantic duplicate merging,
  generalization, embeddings, retention, and reuse-driven confidence remain
  research. The paired experiment's narrow `Helped` classification does not
  justify tuning or automation.

## Rejected Findings

The following attacks did not expose a v0.5 defect beyond the blockers and
hardening above:

- Typed evidence remains contract-addressed and fails closed on malformed,
  oversized, ambiguous, or unsupported payloads; no decoder guesses by JSON
  shape.
- Episode membership races use optimistic versions and SQLite transactions.
  Repeated consolidation converges through fingerprint uniqueness and
  `BEGIN IMMEDIATE`; the complete accepted aggregate is inserted atomically.
- Workspace ownership is enforced by workspace-scoped queries and composite
  foreign keys. No cross-workspace evidence, assessment, search, or context path
  was found.
- The summary renderer describes association and verified-after order, not
  causality, necessity, or current state. Verification subjects and rules remain
  explicit rather than inflated to a broader scope.
- Historical source and graph meaning is held in immutable snapshot values.
  Current document and graph resolution is reported separately with current,
  changed, deleted, missing, or unavailable status; current chunk/graph UUIDs
  are not treated as historical identity.
- Ordinary current source, task, and Event evidence is assembled before the
  historical Experience budget. Experience remains
  `historical_supplemental` and cannot displace already selected current
  evidence.
- Experience FTS input is tokenized to a small allowlist, quoted, and passed as
  a bound parameter. No SQL or FTS operator injection was found.
- Experience search adds no embeddings. Existing vector retrieval requires the
  exact model and dimension, so v0.5 introduces no incompatible vector-space
  mixing.
- CLI and MCP remain thin adapters over the application facade; core Experience
  modules contain no transport semantics. Events, memories, code/graph state,
  and Experiences remain separate domains.
- No automatic grouping, retention, model-backed consolidation, autonomous
  planning, or dedicated coding-agent harness leaked into the release path.

## Quality Gates

At the reviewed head, formatting, compile checks, Clippy with warnings denied,
the full test suite, performance checks, and diff whitespace checks were green.
The suite includes 221 library tests plus integration, CLI, and MCP coverage;
one real-repository experiment test remains intentionally ignored. Green
mechanical gates do not override the semantic counterexamples above.

## Accepted Architecture Corrections

- D098: accepted Experience aggregates are SQLite-sealed; full workspace
  cascade is the only deletion boundary.
- D099: exact failure identity requires a structured discriminator distinct
  from compatible-only classes.
- D100: later recurrence uses a SQLite-owned ingress/acceptance frontier.
- D101: Experience context applies one authority order before every bound and
  uses internally consistent lifecycle state.
- D102: assessment writes are idempotent, lifecycle projection is bounded, and
  history is paged.
- D103: semantic and resume context plus Event projections have service-level
  hard ceilings, with bounded normalized scopes.

## Next Boundary

Breakpoint 13 is complete. The next planned phase is **Final Hardening** on
GPT-5.6 Terra/high. That phase implements B1-B8, incorporates the accepted
hardening items proportionally, updates the README/release surfaces where
needed, and reruns the full v0.1-through-v0.5 regression gate.
