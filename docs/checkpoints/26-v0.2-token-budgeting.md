# Checkpoint 26: v0.2 Token Budgeting

## Result

PASS. Phase 8 assembles a bounded `ContextPacket` from the ranked candidate
pool using the embedding provider's shared token accounting.

## Verified Behavior

- Configurable soft allocations cover code, structural code, memories, events,
  and task or session state.
- Required active-task and pinned items survive bounded candidate retention and
  are selected first; only required items may be UTF-8-safely truncated to the
  remaining total budget.
- Ordinary oversized sources are skipped, unused category capacity is reclaimed
  greedily, and same-path overlapping code content is not duplicated.
- Tiny 2, 4, 8, and 16-token packets retain required task state without
  exceeding their budget.
- A mixed stress case with many high-value code chunks, a huge source, many
  memories, events, required state, and overlapping code remains bounded and
  reports an exact item-token total.
- A storage-backed one-item candidate pool keeps active task state ahead of
  stronger ordinary matches, and exact-tokenizer overhead for empty content is
  never reported as zero.

## Boundary

Token budgeting is deterministic context assembly. It consumes ranked
transport-neutral candidates and the existing embedding token-counter
abstraction; it does not invoke providers, parsers, or adapters directly.
