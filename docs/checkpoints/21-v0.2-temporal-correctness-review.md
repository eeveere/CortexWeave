# Checkpoint 21: v0.2 Temporal Correctness Review

## Result

PASS after two correctness fixes. Bounded temporal retrieval now preserves
current truth, and one-sided timestamp filters validate correctly.

## Adversarial Cases

- An old but current code chunk remains ahead of a newer historical memory and
  event, including when the requested limit is one.
- A newer decision is returned while its explicitly superseded predecessor is
  excluded by default and marked `Superseded` when requested.
- A recent event receives a higher standalone recency score than an older
  decision, but both remain historical evidence. Temporal retrieval makes no
  semantic relevance claim; later candidate ranking must combine relevance and
  recency rather than substituting one for the other.
- A code chunk edited inside a modified-after window is selected while an
  unchanged older chunk is excluded.
- Previous-session resolution is workspace-scoped, and a structured checkpoint
  retains the selected previous session's provenance.

## Corrections

The SQLite candidate limit previously ran after pure recency ordering but before
the service's freshness ordering. A small limit could therefore discard current
source before the service saw it. Candidate ordering now applies the same
current, historical, and superseded classes before the limit.

Optional timestamp bounds were previously compared as `Option` values, which
made an after-only filter invalid because `Some` sorts above `None`. Range
validation now rejects only two present bounds whose after value exceeds their
before value.

## Boundary

Structured checkpoints remain resume state rather than a `ContextSourceType`,
matching the v0.2 source taxonomy. Phase 4 owns checkpoint create/latest/task/
session APIs. Phase 5 and the later ranking phase own the integration assertion
that semantic relevance outranks an irrelevant item's mere recency.
