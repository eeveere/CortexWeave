# v0.5 Checkpoint 78: Experience Assessments and Historical Inspection

**Date:** 2026-08-31

**Scope:** Phase 8 on GPT-5.6 Terra/high

## Result

Experience lifecycle is now governed by an explicit reviewed operation. The
operation validates the reviewer, reason, evidence-event references, target
workspace, replacement target for supersession, and immutable evidence bounds
before SQLite appends the assessment. Existing SQLite append-only and cycle
triggers remain the final transactional enforcement.

The recurring-failure detector is a separate read-only API. It accepts only
events that decode through a registered evidence contract and normalize exactly
to the supplied canonical failure signature. It proposes disputes only for
active prior successes with `verified_passed` verification. Creating a proposal
does not write an assessment or change lifecycle.

Experience search exposes `include_historical` as an explicit historical
inspection intent. Empty lifecycle filters still mean active-only for ordinary
search and context. Historical hits identify the admission cause; experience
detail continues to return the complete immutable assessment history and final
lifecycle, explaining why an old success is no longer normal context.

## Verification

The focused Phase 8 scenario proves this sequence:

1. A verified successful repair is consolidated from typed immutable events.
2. A later event produces the exact same normalized failure signature.
3. The detector proposes a dispute while the Experience remains active.
4. A reviewed dispute removes it from normal search eligibility.
5. Explicit historical search returns it with `historical_inspection` admission,
   and detail inspection exposes the dispute assessment and disputed lifecycle.

Focused service and repository search tests passed. The next breakpoint remains
unstarted.
