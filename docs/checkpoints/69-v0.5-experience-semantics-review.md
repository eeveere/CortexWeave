# v0.5 Checkpoint 69: Experience Semantics Review

## Result

Breakpoint 4 passes. A hand-constructed Experience is explainable field by
field from durable typed evidence, and no consolidation algorithm has landed.

## Semantic Decisions

### Experience versus memory

An Experience is an immutable, bounded interpretation of one terminal episode.
It records observed failure, attempts, following verification, historical
snapshots, and strength provenance. It is not an explicit user-authored memory,
does not enter the memory taxonomy, and cannot promote an associated sequence
into a generalized lesson or causal rule.

### Immutable boundary

The Experience row, ordered verification observations, attempts, evidence
links, strength bases, code snapshots, graph snapshots, renderer version,
summary, fingerprint, and proposal hash are immutable. The only later writes
are append-only assessments and their evidence. Workspace deletion may cascade
the domain; narrower application operations expose no delete or update path.

### Outcome meaning

- `Success` requires at least one scoped passed verifier observation or an
  explicitly accepted scope, no failed observation, and at least moderate
  authoritative evidence. It proves only the recorded subjects passed or were
  accepted at that historical time.
- `Failure` requires a scoped failed observation, no positive observation, and
  at least moderate authoritative evidence.
- `PartialSuccess` requires both positive and failed observations for distinct
  criteria. Conflicting results for one criterion remain `Inconclusive`.
- `Inconclusive` covers conflicting, missing, or unsupported verification.
- `Abandoned` requires an explicitly abandoned episode. An abandoned episode
  may otherwise support only a failed Experience through explicit review.

No outcome says that an attempt caused a verifier result, that every changed
file was necessary, or that a broad pass proved an unrelated criterion.

### Attempts and evidence

Every attempt owns at least one ordered `attempt_change` evidence link. A
conclusive result also owns one following `attempt_verification` link whose
decoded material supports the result. Change and following-verifier links
cannot be orphaned or shared between attempts. Each event has one unambiguous
relation inside an Experience. Phase 5 design further confines the overall
verification observations to the final result frontier, so an earlier failed
attempt does not conflict with a later verified pass.

`StillFailing` means Phase 5 observed the same normalized failure after the
attempt. `VerificationChangedFailure` means it observed a different normalized
failure. `VerificationPassed` means the following event has positive and no
failed scoped observations. `Inconclusive` has no conclusive observation. The
same/changed comparison remains Phase 5 work; the storage proof demonstrates
that exact typed events produce equal and unequal normalized keys.

### Later conflict and retrieval

Review appends an assessment and never rewrites history. Lifecycle derivation
is monotonic with `Superseded` taking priority over `Refuted`, then `Disputed`,
then `Active`; a later `Confirmed` assessment cannot erase a negative state.
Ordinary Experience retrieval must exclude all three negative states by
default. Historical inspection retains the original record and full review
trail. A superseded assessment names one replacement, and SQLite rejects a
second replacement or a cycle.

### Historical intelligibility

Code snapshots own their path, optional symbol/graph keys, exact content,
content hash, and observed document revision. The hash is recomputed before
persistence. Graph snapshots own bounded serialized material rather than a
cascading current-node reference. The record therefore remains readable after
current chunks, symbols, files, or graph nodes are deleted or renamed; stored
paths and keys are historical provenance, never claims about current source.

### Relation truth boundary

SQLite requires all cited Experience events to be members of the source
episode and constrains relation/event-type pairs:

- `initial_failure`: compiler, test, or external-tool completion;
- `attempt_change`: source create/modify/remove/rename or external-tool
  completion;
- `attempt_verification` and `terminal_verification`: compiler, test,
  registered-tool completion, or user acceptance;
- `supporting`: any episode member, without granting verification meaning.

Verification observations must point to a verification relation and preserve
status, kind, subject, exact event, and rule identity/version. Moderate or
strong claims require an authoritative structured basis; user acceptance and
repeated-deterministic bases must match the observations they describe.

## Hand-Constructed Proof

The repository fixture constructs a closed debugging episode with exact
workspace/session/task scope and these typed members:

1. a decodable Rust compiler `E0308` failure for target `core-tests`;
2. a decodable source modification for `src/lib.rs` with revision and BLAKE3
   content identity;
3. a decodable passing Cargo test result scoped to `core-tests`;
4. a decodable failing Cargo test result scoped to
   `other::still_fails`;
5. the same normalized compiler failure after an attempt; and
6. a changed normalized compiler failure after an attempt.

The failure signature is produced by the registered normalizer from event 1,
not copied as arbitrary text. The source snapshot content hashes to the value
reported by event 2. Events 5 and 6 prove equal and unequal normalized keys.
The fixture then validates and round-trips an inconclusive record, validates
`StillFailing` and `VerificationChangedFailure` attempt forms, persists a
scoped successful record, and validates partial success only when the passed
and failed criteria differ.

The deterministic summary is regenerated and compared before persistence. It
renders only the structured failure domain/scope, attempt count, verification
status and subjects, outcome, and the explicit causal-humility sentence. Free
form verification reasons are not rendered into the summary.

## Acceptance Boundary

The aggregate insertion primitive is crate-internal and has no public facade
method in Phase 4. Phase 5 must supply the only production caller after it
implements typed decoding, rule/scope validation, failure comparison,
fingerprinting, and proposal acceptance. Public callers may read Experiences
and append/read reviewed assessments, but cannot submit a self-declared
verified Experience.
