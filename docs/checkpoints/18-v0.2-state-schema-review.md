# Checkpoint 18: v0.2 State Schema Review

## Result

PASS. The Phase 1 schema keeps persistent truth, temporary activation, and
historical evidence as separate concepts.

## Lifecycle Classification

- Memories, explicit supersession, and checkpoints are durable state.
- Working-set entries are persisted temporary activation. Their score and last
  activation time allow Phase 2 to decay them deterministically after restart.
- Pins are explicit session/task priority and remain separate from activation.
- Events remain append-only historical evidence and are not promoted into
  working-set truth by the storage layer.
- Source freshness is a context-time classification. It is not written onto
  source rows where it could become stale.

## Ownership and Integrity

Composite foreign keys enforce that working-set entries, pins, and checkpoints
use sessions and tasks from the same workspace. Memory supersession uses two
workspace-qualified memory foreign keys, preventing cross-workspace replacement.

Working-set and pin source IDs are polymorphic across code, documents, memories,
events, tasks, and sessions. SQLite cannot attach one foreign key to those
different tables. `ContextService` must therefore resolve each source ID and
verify workspace ownership before calling the storage methods. Checkpoint
decision IDs require the same application-service validation.

## Migration Safety

The automated upgrade test applies only migrations 0001 and 0002, writes a full
v0.1 fixture, opens it through the current storage layer, and verifies all old
rows plus the four v0.2 tables. No v0.1 table is rewritten or dropped.
