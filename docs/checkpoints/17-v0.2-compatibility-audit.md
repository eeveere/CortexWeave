# Checkpoint 17: v0.2 Compatibility Audit

## Result

PASS. The v0.2 context orchestrator can be layered above the existing v0.1
services without moving retrieval, persistence, or transport responsibilities.

## Findings

- `RetrievalService` returns stable chunk IDs, current source content, paths,
  symbols, languages, and component scores without exposing SQLite or MCP types.
- Sessions and tasks already provide workspace-scoped provenance and lifecycle
  validation. v0.2 state can extend them through separate tables.
- Memories and events are independently stored and retain workspace, session,
  and task provenance.
- Analyzer stable keys identify logical chunks, while persisted chunk UUIDs are
  preserved for unchanged chunks during incremental reconciliation.
- `McpServer` depends on `CortexWeaveService`; no core module depends on MCP.

## Required v0.2 Migration

Migration `0003_context_state.sql` adds four independent state domains:

- `working_set_entries` for temporary, decaying activation
- `context_pins` for explicit session/task attention
- `checkpoints` for structured resume state
- `memory_supersession` for explicit replacement of durable memories

The migration is additive. Existing workspace, session, task, document, chunk,
embedding, memory, event, and FTS rows are not rewritten. Workspace-consistent
foreign keys prevent session/task state from crossing workspace boundaries.

## Boundary Decision

Context orchestration will consume retrieval and state repositories through
transport-neutral services. Retrieval will not call the context orchestrator,
and adapters will only translate context requests and packets.
