# v0.5.1 Checkpoint 90: Normalized Test Evidence

**Date:** 2026-09-04

**Breakpoint:** BP1

## Result

CortexWeave now decodes `cortexweave.test_run_result` v1 through the same
contract-addressed evidence registry as the v0.5 contracts. The core model has
no Vitest objects, Python objects, command execution, or transport types.

Two exact profiles authorize the BP0-qualified environments: Vitest 4.1.10
with Node 24.19.0 and `python.unittest` 3.14.7 with Python 3.14.7. Unknown
profile, producer, runner, or runtime versions decode for inspection but remain
ineligible.

## Semantics

The decoder enforces payload, collection, namespace, text, path, hash, and
artifact limits; unique parent and child identities; valid parent references;
status/error-class consistency; configured retry/repeat markers; checked count
recalculation; and completion/result/exit consistency.

The profile service distinguishes eligible pass, eligible single assertion
failure, and ineligible evidence. Skips, todo/pending cases, execution and run
errors, expected outcomes, subtests, retries, repeats, flaky cases, partial or
watch runs, snapshot writes, replay/cache origin, input drift, and missing
capture provenance remain visible with deterministic reason codes.

Test failure normalization includes the profile, runner, complete selection,
ordered namespace, case name, and error class. It excludes messages, stacks,
times, durations, run IDs, and artifacts. Identity is compatible-only. The
shared scope helper now receives language explicitly: existing Rust compiler,
Cargo test, and `cargo.check` signatures retain `rust`; TypeScript, JavaScript,
Python, or unspecified test evidence cannot inherit it.

## Verification

The contract suite proves both profiles through the native facade, every
distinct parent outcome, partial/retry/repeat/subtest/input-drift rejection,
count and payload-shape conflicts, bounds, unknown profiles, multi-failure
rejection, portable fixtures, and cross-runner identity separation. Existing
evidence decoder, failure normalizer, and architecture boundary suites remain
green.

## Next dependency

BP2 binds passing evidence to the initial complete inventory and verification
inputs, then records compatible failed attempts without claiming exact failure
sameness or difference.
