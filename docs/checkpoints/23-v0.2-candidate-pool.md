# Checkpoint 23: v0.2 Candidate Pool

## Result

PASS. Phase 5 builds a bounded, source-aware candidate pool without introducing
final ranking, token budgeting, or adapter coupling.

## Verified Behavior

- Hybrid code retrieval and temporal evidence merge into one candidate for the
  same stable source ID.
- Hydrated working-set references merge with their direct and temporal forms
  while preserving activation and selection reasons.
- Memory, event, document, task state, and session state are collected through
  their existing provenance-aware storage paths.
- Explicit task and session inputs retain `ActiveTaskReference` and
  `ResumeState` reasons.
- Path and language scopes filter the candidate set, and
  `context.candidate_pool_limit` caps retained candidates deterministically.
- The pool is distinct from a final `ContextPacket`; later phases own structural
  expansion, ranking, deduplication refinement, and token-budget selection.

## Boundary

`ContextService` consumes `RetrievalService` and storage through
transport-neutral interfaces. SQLite resolves stable source identities; hybrid
retrieval already merges semantic and lexical hits for one code chunk. No MCP or
CLI type enters the pool model.
