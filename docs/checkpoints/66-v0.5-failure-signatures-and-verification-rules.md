# v0.5 Checkpoint 66: Failure Signatures and Verification Rules

## Scope

Implemented the Phase 3 bounded failure-normalization layer. It operates only
on decoded evidence and does not alter stored events, episode membership, or
SQLite state.

## Delivered

- Versioned, length-delimited canonical failure signatures with a
  domain-separated BLAKE3 key and bounded component/scope validation.
- Contract-addressed, pluggable normalizer registry for Rust compiler, Cargo
  test, and registered generic-verifier evidence.
- Exact, versioned verifier-rule registry with the initial `cargo.check` v1
  rule; unregistered reports remain unsupported.
- Rust `E0308` expected/found direction, workspace-relative path scope, and a
  visible diagnostic for absent deterministic diagnostic-to-symbol mapping.
- Cargo test signatures that retain stable test/assertion identity while
  excluding raw failure prose.
- Native facade access to normalize previously decoded evidence.

## Boundaries

- No adapter, MCP, CLI, storage schema, episode lifecycle, consolidation, or
  context-retrieval work was added.
- Raw messages, command strings, temporary paths, environment values, and
  inferred symbols are not signature components.
- Incomplete, ambiguous, zero-exit, or unregistered reports yield typed
  unsupported outcomes instead of best-effort signatures.

## Verification

The Phase 3 suite covers canonical ordering and field boundaries, shifted-line
`E0308` equivalence, expected/found direction, missing structured diagnostics,
workspace separation for identically named tests, raw-message exclusion, and
exact generic verifier registration.
