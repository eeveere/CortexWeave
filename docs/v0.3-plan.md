# v0.3 Plan: Harness-Controlled Context

**Status:** Complete on 2026-08-28

## Purpose

v0.3 turns the v0.2 context substrate into a dependable foundation for a
dedicated coding harness. The harness owns workflow policy; CortexWeave remains
the transport-neutral system of record for indexed source, context selection,
working state, explicit memory, events, and checkpoints.

Real MCP trials established two constraints for this release. A general-purpose
client can choose an unintended tool or bypass a context packet with direct file
reads, even when prompted otherwise. A context packet is therefore evidence,
not workflow enforcement. Also, a supported language that is left disabled is
indexed as generic text, which weakens symbol-level retrieval and can make a
rebuild expensive.

## Non-Goals

- CortexWeave does not become an agent runner, execute tools, infer memories, or
  interpret a model's hidden reasoning.
- MCP remains a best-effort adapter and does not become the control plane for a
  reliable harness workflow.
- Analyzer enablement remains explicit; v0.3 may recommend settings but must
  never silently rewrite a caller's language configuration.

## Phase 1: Workspace Readiness and Index Hygiene

Expose a workspace readiness report that compares discovered source languages
with configured analyzers, reports generic-fallback use, and explains when an
analyzer change requires replacement indexing. Report chunk, embedding, and
replacement counts so a caller can see the cost of rebuilding an old generic
index.

Acceptance:

- a Python workspace with `python = false` reports that it is using generic
  fallback and recommends the available Python analyzer;
- enabling an analyzer and reindexing replaces old chunks deterministically;
- no readiness operation changes configuration or starts a reindex on its own.

## Phase 2: Context Quality Acceptance Suite

Extend final-packet evaluation with named implementation-coverage scenarios.
Each fixture declares expected paths and symbols, then verifies that a bounded
packet contains the implementation evidence required to answer the question.

Initial scenarios are based on the OPiHype trials:

- llama-server lifecycle: `ProcessManager.ensure_ready`,
  `ProcessManager.restart`, `MemoryWatchdog`, and the FastAPI lifecycle;
- watchdog restart during an active run: `MemoryWatchdog._begin_restart`,
  `MemoryWatchdog._restart`, `JobRunner._wait_for_watchdog`, and lifecycle
  tests.

The suite must distinguish a packet that merely mentions a topic in plans or
configuration from one that carries relevant implementation code. Existing
recall, precision, MRR, token, duplication, freshness, and latency metrics
remain in place.

## Phase 3: Native Harness Control Contract

Define a small direct-harness contract around `CortexWeaveService`, not a new
agent framework. It must support this explicit cycle:

1. resolve workspace, session, and task;
2. request a bounded context packet with explanation;
3. evaluate packet sufficiency against harness policy;
4. hydrate only selected chunk IDs when more exact source is authorized;
5. record factual tool, compiler, and test events;
6. activate useful evidence, record explicit memories, and create checkpoints.

The harness owns authorization for direct source reads outside the packet and
records any override with its reason. CortexWeave supplies typed requests,
provenance, selection explanations, and durable state, but never chooses or
executes the harness's tools.

Acceptance:

- a direct-facade integration test completes the full cycle without MCP types;
- a policy test rejects an unapproved out-of-packet hydration request;
- every selected or hydrated source retains workspace, path, symbol, and score
  provenance for the harness audit trail.

## Phase 4: Memory Integrity

Retain the deferred v0.2 work as explicit v0.3 scope:

- provenance and trust policy for imported versus human-authorized memory;
- overlap-aware duplicate-token detection using source ranges or segments;
- explicit contradiction and supersession inference as part of memory
  consolidation.

Memory consolidation must remain reviewable and explicit. It may propose a
supersession relation, but it must not silently alter durable memory.

## Phase 5: Final Evaluation and Documentation

Run the full formatter, check, Clippy, unit, integration, context-quality, and
native-harness gates. Document the readiness workflow, control contract,
override audit trail, and the boundary between advisory MCP use and enforced
native-harness policy.
